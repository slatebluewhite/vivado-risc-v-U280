# SSGemm (Shapeshift Gemmini) — 요약

systolic array 를 **런타임에** 접을 수 있게 만든 것 — 16×16 을 8×32/4×64 로, 32×32 를
4×256 까지. 자세한 과정은 `JOURNAL.md` 의 E427–E512 에 있고, 이 문서는 무엇을 만들었고
무엇이 확인됐는지만 모은다.

용어는 원어 그대로 쓴다 (`total_rows`, `MeshWithDelays`, preload, scratchpad bank, ...).

## 왜

systolic array 는 `K < rows` 인 matmul 에서 위쪽 PE 행이 논다. 배열을 `h × (cols·S)` 로 접으면
노는 행이 열로 바뀐다. `h = rows/S` 이고 `S` 는 segment 수다.

## 무엇을 만들었나

새 파일 **14 개** (`generators/gemmini/src/main/scala/gemmini/Shapeshift*.scala`) 와
기존 파일 **7 개** (`ExecuteController`, `GemminiConfigs`, `GemminiISA`, `Configs`,
`Controller`, `MeshWithDelays`, `Scratchpad`) 수정. E548 에서 GEMV 언롤러
(`ShapeshiftGemvLoop`, funct 23/24)가 추가됐다 — tile-by-tile 명령 바운드(E547)를
풀어 접기 이득을 실물화하는 조각. 전부 `patches/gemmini-shapeshift.patch` 로 유지하고,
갱신은 `experiments/refresh-patch.sh` 로만 한다 (아래 "패치 갱신" 참조).

| 조각 | 하는 일 |
|---|---|
| `ShapeshiftMesh` | 행마다 vertical chain 을 끊을 수 있는 `Mesh` |
| `ShapeshiftMeshWithDelays` | 위를 쓰는 `MeshWithDelays` drop-in. segment 별 `a` skew, scatter, gather |
| `ShapeshiftIsa` | shape 를 `config_ex` rs1[12:10] 에 싣는 인코딩 |
| `ExecuteController` 수정 | shape decode, segment→scratchpad bank fetch, segment→accumulator bank write, D preload 의 reverse index |
| `ShapeshiftSeq`, `ShapeshiftDatapath` 등 | 독립 sequencer 와 단계별 검증 harness |

**ISA 자리**: `config_ex` rs1[12:10]. `CONFIG_EX_RS1_SPACER1`([15:10]) 안이라 기존 필드가 하나도
안 움직이고, shape 를 안 쓰는 프로그램은 0 을 읽어 안 접힌 모양이 된다.

**accumulator 는 안 넓혔다**: segment `s` 를 bank `w_bank+s` 에 쓴다. `io.acc.write` 는 원래부터
bank 별로 있었고 실행 컨트롤러가 하나만 몰고 있었다. scratchpad 읽기도 대칭으로 같다.
**단, "하나만 몰고 있었다" 가 바로 함정이었다** — 뱅크들이 공유하는 accumulate adder
(`AccPipeShared`, Mux1H 선택)가 다중 뱅크 동시 쓰기에서 깨져서, `maxSeg>1` 이면 뱅크마다
자기 adder 를 줘야 한다 (E508, Scratchpad.scala 수정). 그 수정의 면적은 격리 OOC 실측으로
**LUT -1,008 / FF +1,536** (banks=4, cols=16, E512) — 넓은 Mux1H 를 없애는 것이 가산기
복제보다 싸서, 수정이 LUT 로는 오히려 이득이다.

## 확인된 것

### 정확성 — 검사기 넷과 각자의 사각지대

| 검사기 | 보는 것 | 못 보는 것 |
|---|---|---|
| `ShapeshiftEquiv` | 접힌 mesh = stock `Mesh` S 개 | mesh 밖 |
| `ShapeshiftMWDEquiv` / `Seg` | `MeshWithDelays` 프로토콜 전체, shape=0 에서 stock 과 사이클 동일 | 명령 해석 |
| `ShapeshiftExecSeg` | segment 독립성, bank 라우팅 | 양쪽이 같이 틀리는 오류 |
| `ShapeshiftExecXTop` | shape 끼리 같은 답 + **절대 Scala golden** | — |

> **[E507/E508 — 반드시 먼저 읽을 것]** 아래의 E506 까지의 정확성 검증은 전부 **지연 0 의
> 가짜 누산기** 위에서 이뤄졌다. 진짜 `AccumulatorMem` 을 물리자(E507) **chunk>1 인 접힌
> shape 가 전부 틀렸다**: stock Scratchpad 의 공유 `AccPipeShared` 는 `Mux1H` 로 뱅크를
> 고르는데, 접힌 shape 는 같은 사이클에 S 개 뱅크에 accumulate 를 넣어 다중 선택으로 깨진다
> (충돌 비트가 실패 비트와 정확히 일치, E508). **수정됨**: `shapeshift_max_segments > 1` 이면
> Scratchpad 가 뱅크마다 자기 adder 파이프를 준다 (stock 경로 불변). 수정 후 진짜 누산기에서
> 8x8 maxSeg=8 (h=1 포함)과 16x16 maxSeg=4 가 golden 일치, 음성 대조 발화, 공유로 되돌리면
> 재실패. **정확성의 최종 판정은 accMode=2 (진짜 누산기 + per-bank adder) 기준이다.**
> 사이클 모형은 진짜 누산기에서 앵커 재측정으로 확인됐다 (E509: 16x16 maxSeg=8 네 shape
> 전부 가짜/진짜 동일, 104/48/36/42). 바닥 4 조건에서 write.ready 인터록은 발화하지 않는다.

세 기하(16×16, 8×8, 16×8)에서 세 shape 모두 golden 과 일치하고, 음성 대조 셋이 각각 발화한다.
`maxSeg=8` 에서는 **네** shape(S=1,2,4,8, 즉 h=16/8/4/2)이 모두 golden 과 일치한다 (E494).
**32×32 도 검증됐다 (E496)**: h=32/16/8/4 네 shape 모두 golden 일치, 음성 대조 발화 —
첫 시도에 통과. 검증 범위는 배열 8/16/32, h 는 32 부터 1 까지, chunk 는 4 까지다. (E543 에서 maxSeg=16 시퀀스까지 포함해 봉투가 닫혔다 — 가드 후 재검증 누계 36/36.)
**[E517~E526 대형 passes 사냥 — 종결]** 위 격자는 passes(=ch·nt) <= 4 위주였고,
passes 가 크면 실패하는 현상이 있었다. 아홉 항목(E517~E525)에 걸쳐 발현 법칙과 데이터
패턴을 좁힌 끝에 원인은 **하네스 SSExecUnit 의 fill 카운터 8비트 슬라이스**로 확정됐다
(E526) — `NFILL > 256` 이면 wrap 해 B 의 마지막 행들이 영영 안 써졌다. "K%h==0" 조건은
부분 chunk 의 읽기 창이 그 안 쓰인 꼬리에 닿지 않는 것이었고, mode-2(값 전부 0)는 wrap
규모가 커진 같은 결함이다. E523 의 "A 피드 truncation" 은 잘린 곱 항 집합까지는 정확했으나
귀속이 틀렸다 — W 역산은 A-측 0 과 B-측 0 을 구별하지 못한다(실제는 B). **수정 후 실패
전 칸 재검증 10/10** (음성 대조 발화, 회귀 없음). **RTL 은 대형 passes 에서도 무죄**이고,
E508(공유 adder)·E518(id alias)은 이와 무관한 진짜 RTL 기전으로 유효하다.
**전 계열이 진짜 누산기(accMode=2, E508 수정 포함)에서 재검증됐다 (E511)**: 임의 K·N(E480),
런타임 전환(E482, phase 경계까지 가짜 acc 와 동일), 32x32(E496), 각각 음성 대조 발화.

**total_rows 바닥 2 는 조건부 재해금됐다 (E516 -> E517 -> E518).** E511 이 확정한 assert(EC 의 무-backpressure)
는 E516 의 skid queue 로 풀렸고 (h=2·ch=2·nt=1, h=1·ch=4·nt=1 에서 golden 통과), 바닥 4
경로는 netlist 불변이다. 그러나 **(h=2, ch>=4, nt>=2) 에서 정확성 회귀**가 나왔다 (E517) —
회귀의 범인은 `matmul_id` 의 mod-5 wrap 이었다 (E518): 바닥 2 에서 동시 진행 matmul 이
5 를 넘어 id alias -> 출력 태그 오매칭. 실패 지도는 "h=2 이고 passes>=8" 이었고, 바닥 < 4
일 때만 id 공간을 `max(5, ceil((h_min+cols+8)/floor)+2)` 로 넓히는 개입으로 전 칸이
청소됐다 (real acc 포함, 음성 대조 발화, 바닥 4 경로 불변). **검증 격자: 8x8 의 18칸 —
32x32 와 passes=6 경계는 미검이므로 바닥 2 를 쓰려면 그 격자를 먼저 채울 것.**
**유량 한계와 그 해법 (E527 -> E528)**: tile-major 발행에서는 같은 주소 누적의 도착
간격(2)이 서비스 간격(3)보다 짧아 적체가 무한히 자라고(depth-4 큐가 ch=4·nt=4 에서
overflow — E516 의 지속 유량 논증 반증), 실효 바닥이 3 으로 깎였다(8x8+L2 1.33x).
**chunk-major 발행(tt 바깥 루프)이 이것을 스케줄만으로 푼다** — 재방문 간격이 nt·tr 로
벌어져 nt>=2 면 stall 0, E527 에서 죽던 칸까지 5/5 예측 일치 (E528). 사이클 모형(바닥 2
최종): 치환모형 + 1 (chunk-major·nt>=2), + (ch-1) 추가 (nt=1). **컴파일러 규칙: 바닥<4
하드웨어에서는 K-분할을 chunk-major 로 발행할 것.** 이로써 8x8+L2 decode 의 **1.50x**
(2.00 -> 3.00x) 가 성립한다 — 조건은 N > cols·S (decode 의 큰 N 은 넉넉히 만족).
**면적 비용은 +1.0~3.3% LUT** (E529: 8x8 +1,304 / 16x16 +1,397 — skid queue 저장이
LUTRAM 으로 가서 FF 는 거의 안 는다). 바닥 2 인도물(정확성·모형·스케줄 규칙·면적)이
이로써 완결. (한동안 미검이던 32x32 maxSeg=16 은 E543 에서 하네스 sp_banks 32 확장으로
정확성까지 6/6 검증됐다. 바닥 2 와의 조합도 E544 에서 3/3 — 미검 조합 없음.) 바닥 4 가 지키던 가정은 셋: ROB retire(>=2), 누산기 WAW(>=4 — E516 queue
는 과도 구간용이고 지속 유량은 못 푼다), id 공간(E518 산식으로 해소).

**런타임 전환도 확인했다 (E482)**: 한 `ExecuteController` 에서 `config_ex` 로 shape 를 바꿔
가며 두 matmul 을 돌리면 양쪽 다 golden 과 맞는다 (S=1↔S=4, S=1→S=2). 두 번째 `config_ex` 가
같은 shape 를 보내도록 만든 음성 대조는 실패한다 — 전환이 실제로 원인이라는 뜻이다.
**"전환 비용" 은 전환의 비용이 아니었다 (E486 -> E535 재명명)**: 대각(같은 shape 재-config)
포함 9칸 격자에서 값은 **출발 shape 만의 상수** c(from) = +1 (S=1, S=4) / +3 (S=2) 이다 —
같은 shape 를 다시 config 해도 똑같이 드는 **drain-to-ready 간격**이지 전환 기계의 비용이
아니다. E486~E489 가 좁힌 "출발 shape 의 성질(h=8)" 은 방향이 맞았고, 프레임("전환")이
틀렸다. 실용 함의는 강화된다: shape 선택은 이 상수와 완전히 독립이므로 **컴파일러는
matmul 마다 자유롭게 shape 를 고르면 된다** (같은 shape 연속도 이득 없음). 바닥 2 에서는
같은 방법의 격자가 순수 측정 오프셋만 남겼다 (E534 — 실비용 0~3 규모 동일).

**개정 (E537~E541): 위의 +1/+3 은 가드 이전 하드웨어의 성질이다.** 그 값이 작았던
이유는 phase 경계가 파이프라인되기 때문이었는데, 바로 그 겹침이 ms8·32×32 시퀀스를
깨뜨리는 통로였다 (total_rows·sp 읽기 뱅크·acc 쓰기 라우팅이 live shape_reg 를 봐서,
다음 phase 의 config 가 진행 중 matmul 의 창을 오염 — E540 트레이스로 확정). 수정은
config_ex 를 feed 유휴 + mesh drain + 4사이클 정지까지 지연하는 구조 가드(E540)이고,
그 후 **전 기하 25/25 PASS** (E541 — wedge 소멸, S=8 상부 세그먼트 전폭 검사 포함).
현행 전환 비용은 27/27 경계에서 from-shape 만의 상수:

| D(from) | S=1 | S=2 | S=4 | S=8 | S=16 |
|---|---|---|---|---|---|
| 8×8 | +21 | +19 | +13 | — | — |
| 16×16 | +37 | +31 | +25 | +25 | — |
| 32×32 | +69 | +55 | +51 | +43 | +37 (E543) |

maxSeg 무관, to-무관, 대각 포함. BERT급 matmul 에서 <0.5% — "matmul 마다 자유롭게
고른다"는 함의는 유지된다. 파이프라인 복원(0~3 사이클로 되돌리기)은 shape 를 mesh
tag 에 태우는 확장으로 가능하며 미구현 옵션으로 남긴다.

**크기에 따른 변화 (E491)** — `ExecuteController`, maxSeg=4:

| n | LUT +% | FF +% | Δ지연 |
|---|---|---|---|
| 8x8 | 14.62% | 20.67% | +0.429 ns |
| 16x16 | 7.01% | 9.39% | +0.294 ns |
| **32x32** | **3.67%** | **1.69%** | **+0.031 ns** |

**배열이 커질수록 모든 면에서 싸진다.** 접는 기구는 둘레(스큐 mux, gather/scatter, 넓은 acc
포트)에 붙고 mesh 만 넓이로 크므로 ΔLUT 는 O(n), 비율은 1/n 이다 (측정 배수 1.79/2.03).
지연도 무너진다 — 큰 배열에서는 임계 경로가 mesh 쪽으로 옮겨 가 스큐 mux 가 빠진다.
**단 이 지연 곡선은 `maxSeg=4` 단면이다**: 같은 32x32 에서 `maxSeg=8` 은 +0.306 ns 로
열 배 늘어난다 (E495). 배열 크기와 shape 표 깊이가 지연을 반대로 민다.

`M` 이 작은 workload 에서는 큰 배열일수록 낭비도 크므로 **비용이 가장 싼 곳이 이득이 가장
큰 곳**이 된다. 다만 이것은 workload 조건부다 — `N` 이 좁으면 반대로 간다 (E497, 아래).

**사다리 깊이 (E492/E493)** — `maxSeg` 를 자기 뱅크 수와 짝지어 16x16 에서 측정:

| maxSeg | 이득 (decode GEMV) | LUT 비용 |
|---|---|---|
| 2 | 2.00x | **+0.15%** |
| 4 | 3.99x | +7.01% |
| 8 | **3.99x (이득 없음)** | +18.61% |

`total_rows = max(M,h,4)` 의 4 바닥 때문에 `h<=4` 면 더 접어도 안 준다 —
**쓸모 있는 최대 maxSeg 는 `rows/4`** 이고, 그 이상은 되레 느려진다.
한계 이득은 1->2 가 나머지 전부보다 **23배** 남는다 (E510 정정 — 원문 20배는 자기 수치에서 재현되지 않음). 재뱅킹 비용은 무시할 만하다 (+0.78%).

**권장표 (E491~E495)** — **면적 열은 전부 실측**이고, decode 이득 열은 **사이클 모형
산출값**이다 (compute 스케줄만 — E498 의 roofline 아래에서 decode 는 이 보드에서 1.00x).
각주: 16x16 ms2 는 acc_banks=2 로, 32x32 ms2 는 acc_banks=4 로 잰 값이라 뱅킹 조건이 다르다
(각자의 ms1 기준선과는 같은 조건이므로 Δ는 유효). 8x8 ms2 실측은 35,069 LUT (E510).

| 배열 | maxSeg | decode 이득 | ΔLUT | +% | %p 당 배수 |
|---|---|---|---|---|---|
| 16x16 | 2 | 2.00x | 193 | +0.15% | **13.3** |
| 16x16 | 4 | 3.99x | 8,994 | +7.01% | 0.57 |
| 32x32 | 2 | 2.00x | 1,274 | +0.26% | 7.7 |
| 32x32 | 4 | 3.98x | 18,227 | +3.67% | 1.08 |
| **32x32** | **8** | **7.89x** | **48,424** | **+9.74%** | 0.81 |

두 축은 **분리되고 곱해진다**: `ΔLUT(n, maxSeg) = C·n·g(maxSeg)`, `g(2)≈0.06, g(4)=1,
g(8)=2.66, g(16)=10.52` — maxSeg 비가 배열 크기 간에 2.66/2.66, 2.06/2.0 으로 네 점
전부 선다 (E495/E531). 사전등록한 32x32 ms8 예측은 오차 **0.16%**. 단 **g 의 꼬리는
이차다** (비율 2.66 -> 3.96, 4 에 접근): 사다리가 길어지면 gather/scatter 가
`cols·maxSeg` 폭 crossbar 로 자라기 때문 — maxSeg 축은 "둘레" 가 아니다. ms16 은
+72.5%(16x16)/+38.9%(32x32) LUT 로, 바닥 2 + B>4·cols 대역에서만 의미가 있다.

**측정으로 확인됨 (E494)**: 16x16 `maxSeg=8`, `(4,8,64)` 에서 네 shape 모두 절대 golden 과
일치하고(h=2 가 ISA 수준에서 처음 검증), 사이클이 모형과 **정확히** 일치한다 —
S=1/2/4/8 = 104/48/36/42, 오차 0. `S=8` 은 out-of-sample 이다 (모형은 h=16/8/4 에서만
맞춰졌었다). 그리고 **S=8 이 S=4 보다 느리다** (42 vs 36): N 타일은 같은데 chunk 가 2->4 로
늘어서다. `rows/4` 는 모형 예측이 아니라 측정된 사실이다.

**타이밍**: `ExecuteController` 16x16 의 OOC 임계 경로는 5.451 -> **5.745 ns** (+5.4%, E481).
늘어난 것은 스큐 망의 mux 한 단으로 읽히지만, E492 는 지연이 maxSeg 에 단조가 아님을
보였다 (5.451/5.897/5.745 — ms2 가 ms4 보다 느림). 지연 숫자는 0.1~0.4 ns 수준에서
신뢰하지 말 것.

이 보드에서는 **실질적으로 공짜**다 — 추론이지 측정은 아니다. U280 의 Rocket/Gemmini 도메인
상한은 62.5 MHz(16 ns)다 (E314/E320 — 19 ns 짜리 `scale_func` 조합 사슬을 shared-unit 으로
재구조화해 닫은 주파수). 5.745 ns 는 16 ns 예산에서 10 ns 이상 떨어져 있어서, 전체 SoC 배치가 이 경로를
두 배로 나쁘게 만들어도 여유가 남는다. OOC 수치와 배치 후 수치를 직접 비교한 것은 아니므로
접이식 비트스트림을 실제로 지으면 확인해야 한다 — 이 트랙에서는 짓지 않았다.

`maxSegments=1` 은 FIR 비교로도 확인 — `ExecuteController` +1 줄(shape tie-off), mesh 밖 +0.
고정 16×16 과 고정 4×64 를 **둘 다** 지으면 LUT 56,697 / PE 512 인데, 접이식 하나는
30,834 / 256 이다 (LUT 45.6%, PE 50% 절감).

### 성능 — 정확한 사이클 모형

    cycles = (passes - 1) * total_rows + M + h + max(h,4) + cols + 4
        passes     = ceil(N/(cols*S)) * ceil(K/h)
        total_rows = max(M, h, 4)
        h          = rows/S

측정 **74 칸**(네 기하, K·N 이 임의인 경우 포함)에 오차 0. 그중 12 칸은 사전등록된 out-of-sample. 자유 파라미터는 `+4`
하나뿐이고 나머지는 구조에서 온다.

**배열 크기 out-of-sample (E496)**: 사이클을 잰 것은 전부 `rows <= 16` 이었는데, 32×32 에서
재보니 네 shape 모두 오차 0 (136/72/56/52). 모형은 rows 8~32, h 32~2 에서 검증됐다.
단 **모형이 맞다는 것과 어떤 shape 에서 얼마를 번다는 것은 다른 진술이다** — 이 shape 의
S=1→S=8 은 2.62배이고(드레인 지배), 권장표의 7.89배는 같은 모형을 decode GEMV 에 넣은 값이다.

이득의 원천은 셋이고, 각각 사라지는 조건이 있다:

| 원천 | 언제 사라지나 |
|---|---|
| pass 수 `ceil(N/(cols·S))` | N 이 좁으면 (clamp) |
| pass 길이 `max(M,h,4)` | M 이 크면 |
| 드레인 `h + max(h,4)` | 사라지지 않는다 |

실측 예: `(4,4,64)` 3.25배, `(16,4,64)` 2.64배, K 분할한 `(4,16,64)` 2.36배,
그리고 **`(16,16,16)` 에서는 0.74배로 진다** — 접기가 항상 이기지 않는다.

### 무엇을 사는가

`experiments/mlir/workload.py` 가 모형으로 계산한다:

| workload | 이득 (16×16) |
|---|---|
| BERT prefill (M=128, K 큼) | 1.00× |
| **decode GEMV (M=1)** | **4.00×** |
| **ResNet 1×1, C_in=3** | **3.98×** |
| depthwise 3×3 (N 좁음) | 접으면 지고, 규칙이 안 접는다 |

> **[E498 에서 크게 깎임] 위 표는 compute 스케줄의 사이클 수다.** 이 보드의 실측 대역폭
> (DRAM 4.75 B/cycle 읽기, L2 24.04)을 넣어 roofline 을 다시 계산하면 **decode 계열의
> 이득은 1.00x 로 사라진다** — weight 를 통째로 스트리밍하므로 배열이 이미 98 % 놀고 있고,
> 접어서 compute 를 4 배 줄여도 기다리는 시간은 그대로다.
>
> | workload | compute | **실제** |
> |---|---|---|
> | LLM decode GEMV (16x16 / 32x32) | 4.00x / 8.00x | **1.00x** |
> | BERT decode projection | 3.99x | **1.00x** |
> | ResNet 1x1, C_in=3 | 3.98x | **1.44x** |
> | small batch K=8 | 3.56x | **1.62x** |
>
> 구조적이다: 이득은 `M < h` 에서만 나는데 compute-bound 는 `M >= rows*cols/B` 를 요구하고,
> peak 은 `rows^2` 로 크는데 창은 `rows` 로만 큰다 — **배열이 커질수록 창이 닫힌다.**
> 16x16 + L2 상주(`M` 11~15)만 남는다. 살아남는 것은 pass 수 원천(N 타일)이고, 그래서
> **작고 L2 에 드는 작업**(얕은-K conv, small batch)이 실제 대상이다.

**최종 (E499, 양쪽 다 최적 `M` 으로 튜닝한 뒤):**

| workload | 실제 이득 |
|---|---|
| ResNet 1x1 C_in=3 (N=64 / 256) | **1.44x / 1.49x** |
| ResNet conv1 7x7 K=147 | 1.08x |
| MobileNet pointwise K=32 | 1.01x |
| BERT / LLM decode | 1.00x |

**현실적 천장은 1.5x 이고 `K <~ h` 인 층에서만 난다** — im2col 후 `K = C_in*kernel^2` 이므로
사실상 **RGB 입력의 첫 층**뿐이다. 1,200 칸을 쓸어 나온 최대 7.22x 는 `M=1` 에서 나는데,
거기는 **접기 없는 기준선이 가장 나쁜 곳**이고 절대 성능은 3.8배 나쁘다 — 기준선을 같이
튜닝하지 않은 착시였다.

**네트워크 단위 (E500, batch 1, roofline):**

| 네트워크 | 접기 이득 | **동적 전환의 이점** |
|---|---|---|
| ResNet-18 (224²) | 1.001x | **+0.00%** |
| ResNet-20 (CIFAR, 전부 L2) | 1.000x | **+0.17%** |
| 가상: K=3 만 8층 (16x16 / 32x32) | 1.486x / 1.000x | +0.00% |

**이 설계의 핵심 기능인 런타임 전환이 네트워크 단위로 0.00~0.17% 다.** CIFAR 에서 층별
선택은 `{S=1:5, S=2:4, S=4:5}` 로 정말 갈리는데 시간은 안 바뀐다 — 선택지가 갈리는 것과
선택이 중요한 것은 다른 명제다.

또한 위 표의 "ResNet 1x1, C_in=3" 은 **실재하지 않는 층**이다 (1x1 conv 의 `C_in` 은
64/128/256 이고, `C_in=3` 인 첫 층은 언제나 3x3/7x7 이다). ResNet-18 의 실제 첫 층은
`K=147` 로 **1.08x** 다.

**대역폭 닫힌 형태 (E501)** — 45 칸에서 오차 0.0%:

    이득 = min(maxSeg, B / cols)     (B 는 B/cycle, B >= cols; maxSeg 는 유효 사다리 h>=4 기준 —
                                      h<4 shape 를 사다리에 넣으면 공식이 깨진다, E510 정정 6)

**xsim 으로 직접 확인 (E502/E503)**: `(1,16,64)` 에서 접은 8x8 이 **81 사이클**, 안 접은
16x16 이 **101 사이클** (모형과 오차 0, 양쪽 golden 일치). 단 그 1.247배는 **유한 크기
효과**다 — N 을 키우면 1.606 -> 1.247 -> 1.019 -> **1.001x** 로 무승부에 수렴한다 (E503).
**무승부가 곧 결론이다**: 같은 사이클을 LUT **27.3%** (실측 35,069/128,269, E510) 로 내므로 LUT 당 **3.66배**.

경계 셋 중 **M 경계만 xsim 실측**이다 (`M` 1→8 에서 81<101 이 **148>108** 로 뒤집힘).
양쪽 모두 real acc 로 재확인됐다: M=1 은 149/81/101 (e510c.log), M=8 은 156/148/108
(e514.log — E514). N 수렴열과 K 경계는 검증된 모형의 계산이다.

조건은 **곱 하나**다 (E504) — E503 의 "별개 조건 둘" 서술은 취소한다:

    이득 = [ceil(K/H)/ceil(K/h)] x [max(M,H,4)/max(M,h,4)]   (H = 안 접은 배열의 행 수)

**4 바닥 (E505, E510 에서 정정)**: `h<4` 면 M 인자의 상한이 `H/h` 가 아니라 `H/4` 로 잘린다.
원문의 "무승부 자체가 불가능" 은 **min/max 혼동 오류였다** — 옳은 명제는 둘이다:
**점근(K>>h)** 곱은 `h/max(h,4)` 로 수렴해 h=2 는 영구 0.5x 이지만, **`K<=h` 에서는**
`H/max(h,4)` 배까지 **이긴다** (h=2,H=32 에서 8배; 모형 검산 7.64배). 설계점 `h=4`
(= `maxSeg=rows/4`) 는 유지되나 근거는 E493(같은 배열 실측)과 "K<=2 인 층의 실질 부재" 이지
전역 불가능성이 아니다.

| | 결과 | LUT 당 |
|---|---|---|
| `B < cols` (E501) | 아무것도 안 됨 | — |
| `cols <= B < 2*cols` | 부분 이득 `B/cols` (선형 램프) | 비례 |
| `K <= h` **그리고** `M <= h` | 3.9배 빠름 | **14.2배** |
| 둘 중 **하나만** | 무승부 | **3.66배** |
| 둘 다 아님 | 최대 4배 손해 | 0.91배 |

`K <= h` 는 im2col 후 `C_in*kernel^2 <= h` 라 실질적으로 없고, `M <= h` 는 batch-1 decode 가
만족한다. **ResNet-18 이 1.001x 인 이유는 `M` 이 아니라 `K` 다** (첫 층 K=147 → K인자 0.27,
깊은 층 K=576~4608). E503 에서 `M` 탓으로 적은 것은 틀렸다.

**접기의 정체는 속도가 아니라 면적 효율이다.** `B >= 2*cols` 인 동안 접은 `n x n` 은
안 접은 `2n x 2n` 과 사이클이 같고 LUT 는 **27.3%** 다 (B=24 에서 8x8 접기 12,583,014 vs
16x16 무접기 12,583,134). 반대로 이 보드의 DRAM(4.75 < cols=16)에서는 세 배열이 전부
같은 사이클이라 배열 크기도 접기도 무의미하다 — E500 이 0.00% 를 본 이유다.

이식 조건은 둘이 **모두** 필요하다: `B >= 2*cols`, 그리고 워크로드가 `M < h`.
`K >> h` 인 층이 지배하면 대역폭과 무관하게 이득이 없다 (ResNet-18 은 B=1024 에서도 1.009x).

**SoC 인도물 (E514/E515/E530/E532)**: `Rocket64b1gem16ss`(16x16, 바닥 4)와
`Rocket64b1gem8ssf2`(8x8, 바닥 2 — skid queue x4, per-bank adder x4 실재 확인) 둘 다
elaboration -> system-u280.v 까지 통과 (E539/E540 수정 반영본으로 E545 에서 재생성). 바닥 2 빌드의 **런타임 전환도 정확성 검증 완료**
(E532~E534 — 양방향·3-phase 연쇄 모두 golden 일치, 음성 발화. **전환 비용은 0**:
동일 문맥 9-시퀀스 격자에서 비용 행렬이 완전 반대칭 = 퍼텐셜 δ(shape)=(0,−2,+2) 로 분해 —
관측됐던 ±2~6 은 phase 끝 측정점의 shape 의존 오프셋이고 시퀀스 전체에서 상쇄된다.
E533 의 ~1/~6 추정은 폐기. **주의: 이 "0" 도 가드 이전 측정이다** — E540 의 정지
가드 이후 전환 비용은 위의 D(from) 표를 따른다. 가드 후 바닥 2 재검증은 완료:
16×16 f2 3칸 + 8×8 f2 2칸 전부 PASS, 첫 phase 절대값은 바닥 2 모형(+1 포함)과
전부 정확히 일치 — E541). Vivado 합성부터는 트랙 범위 밖.

**요약하면**: 면적은 거의 공짜가 맞고 (2-shape +0.15%) RTL 과 사이클 모형도 검증됐다.
그러나 **이 메모리 시스템에서 살 이유가 없다** — ResNet-18 전체에 1.001x, 동적 전환은 +0.00%.
살 이유가 생기려면 대역폭이 한 자릿수 배 늘거나, `K < rows` 인 층이 네트워크의 큰 몫을
차지해야 한다. E428 의 전제("K < rows 면 위쪽 PE 행이 논다")에 해당하는 층은 **CNN 의 첫
층 하나뿐**이었다.

**배열 크기를 축으로 보면 이득의 두 원천이 반대로 움직인다 (E497):**

| workload | 8x8 | 16x16 | 32x32 |
|---|---|---|---|
| prefill (M=128) | 1.00x | 1.00x | 1.00x |
| decode GEMV (M=1) | 2.00x | 4.00x | **8.00x** |
| ResNet 1x1 (M 큼, N 좁음) | 2.00x | **3.98x** | 2.00x |

- pass 길이 `max(M,h,4)` 는 M 이 작을 때만 줄고, 배열이 크면 줄일 여지가 많다 -> **증가**
- pass 수 `ceil(N/(cols*S))` 는 N 이 넓을 때만 줄고, 배열이 넓으면 이미 타일이 적다 -> **감소**

prefill 의 1.00x 는 구조적이다 (`M>=rows` 면 `total_rows=M` 고정, passes 는 S 로 상쇄) —
어떤 배열 크기·사다리에서도 안 는다. ResNet 1x1 은 **16x16 에서 정점**인 내부 최적점을
가진다: 8x8 은 사다리가 짧고(`h>=4`), 32x32 는 N 이 두 타일뿐이다.

**그래서 권장의 축은 배열 크기가 아니라 `M` 과 `N` 이다.** 면적은 클수록 싸지만(E491),
이득은 workload 에 따라 반대로 갈 수 있다 — 이 트랙에서 둘이 엇갈린 첫 사례다.

  Controller busy 수정(E564)을 담은 비트스트림 5판 빌드 중.
- MLIR pass 를 빌드·실행한 적 없다 (이 머신에 LLVM/MLIR 없음). 결정 로직만 따로 검증했다.
- 라이브러리(`tiled_matmul_auto`)는 정사각 `DIM` 을 가정하므로 그대로 못 쓴다.
  backend 는 `experiments/tests/include/gemmini_rt.h` 계열이어야 한다.
- 메모리는 **실측 대역폭을 넣은 roofline 산술**로만 들어가 있다 (E498~E501) — 시뮬레이션에
  DMA·메모리 모형이 있는 것은 아니다. 대역폭 결론의 최종 확인은 보드 측정이 필요하다.
