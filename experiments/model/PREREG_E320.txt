사전 등록 — E320: 62.5 MHz + 공유 스케일 유닛 판의 검증
작성 시각: 라우팅 진행 중, 측정 전.

## 무엇이 걸려 있나

E313이 임계 경로를 `AccumulatorScale`의 조합 `scale_func` 체인으로 특정했고(배선 62%),
E314가 `num_scale_units = 16`으로 그 체인을 끊고 62.5 MHz를 목표로 빌드했다.
배치 후 WNS +0.026, 라우팅 중간 +0.599, TNS 0 — 타이밍은 닫힐 것으로 보인다.

면적: 39.09% LUT / 57.11% CLB (50 MHz 조합 판은 38.50 / 55.11) -> **+0.59 %p LUT**.
레지스터 238,586 -> 249,038 (+10,452) — 유닛별 레지스터가 붙은 것과 일치.

## 검정할 것 세 가지, 순서대로

1. **정확성이 먼저다.** 이 코드 경로(`num_scale_units != -1`)는 업스트림에서 정규화
   구성으로만 쓰였고 내가 세 군데를 고쳤다. 이 프로젝트는 조용히 틀리는 사례를
   여러 번 겪었다(BF16 preload, OUTPUT_STATIONARY, ex_accumulate). matmul이 PASS하지
   않으면 나머지 수치는 의미가 없다.
2. **클럭이 실제로 62.5 MHz인가.** 장치 트리의 timebase로 확인한다.
3. **처리량.** 클럭만 바뀌었다면 같은 워크로드의 시간이 정확히 50/62.5 = **0.800배**여야
   한다. 어긋나는 만큼이 공유 스케일 유닛이 mvout 처리량에 물린 비용(또는 이득)이다.

## 예측

- 정확성: PASS. (근거는 없다 — 코드를 읽었을 뿐이다. 틀리면 그것이 결과다.)
- 시간비: **0.800배보다 크다(=덜 빨라진다).** 공유 유닛은 유닛당 1원소/사이클로
  폭 16을 채우므로 정상 상태 처리량은 같지만, `arbOut` 레지스터와 `out_regs`/
  `completed_masks` 핸드셰이크가 응답당 지연을 더한다. mvout이 compute 뒤에 숨는
  비율만큼 그 지연이 가려지므로 **0.80~0.85 사이**를 예상한다.
- 0.80보다 작게 나오면(더 빨라지면) 측정을 의심한다 — 클럭 외에 빨라질 이유가 없다.

## 판정

- PASS + 시간비 0.80~0.86 -> 성공. **+0.59 %p LUT로 +25% 클럭**이며, 이 트랙에서
  256비트 버스(1.10 %p로 8~10%) 다음가는 면적당 수익이다.
- PASS + 시간비 0.90 이상 -> 공유 유닛의 지연 비용이 크다는 뜻. 클럭 이득의 절반이
  날아간 것이므로 순이득을 다시 계산한다.
- FAIL -> 패치가 틀렸다. 어느 단계에서 틀리는지 좁힌다(mvin -> 누산 -> mvout).

## 측정

`bus2`(서명), `m2_base`·`m2_large`·`m2_h1536` (m<=2만 — custom1 없음).
프로세스 5회, `chrt -f 99`, 최소값. 비교 대상은 같은 이진의 50 MHz 2가속기 판 결과
(`hw2_*.log`, E309).

주의: 프로그램의 루프라인 계산은 FREQ=50e6이 하드코딩돼 있으므로 **η 수치는 무시**하고
절대 시간(ms)만 쓴다.
