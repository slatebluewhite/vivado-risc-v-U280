E497 사전등록 — workload 판정을 배열 크기 축에서 다시 계산한다

현재 판정('접기는 batch-1 기능, decode 4배, ResNet 1x1 3.98배')은 전부
16x16 / maxSeg=4 에서 나온 것이다. 모형이 이제 32x32 와 h=32~2 까지 검증됐으니
(E494/E496) 배열 크기를 축으로 다시 볼 수 있다.

모형 구조에서 **정반대 예측**이 나온다 — 두 계열이 반대로 움직인다:

  [A] decode 류 (M=1, N 큼): 이득은 total_rows = max(M,h,4) 가 h 를 따라 주는 데서
      온다. 배열이 크면 h 도 커서 줄일 여지가 많다. -> **커진다** (상한 rows/4)

  [B] 얕은 K + 좁은 N 류 (ResNet 1x1: K=3, N=64): M 이 커서 total_rows 는 M 으로
      고정이고, 이득은 오직 N 타일 수 ceil(N/(cols*S)) 에서 온다. 그런데 배열이
      넓으면 접기 전에 이미 N 이 몇 타일 안 된다. -> **줄어든다**

[예측] 16x16 -> 32x32 로 갈 때
  [1] decode GEMV:   4.00x -> **약 8x** (증가)
  [2] ResNet 1x1:    3.98x -> **약 2x** (감소)
  [3] prefill(M=128): 1.00x -> **1.00x** (정확히 불변). M >= rows 이면 total_rows=M 이고
      passes 도 S 에 대해 불변이라 구조적으로 이득이 0 이다.

맞으면: '큰 배열일수록 접기가 좋다' 는 E491 의 면적 결론이 성능에서는 **workload 에
        따라 반대**라는 뜻이고, 권장이 '배열 크기'가 아니라 'M 과 N' 으로 갈린다.
